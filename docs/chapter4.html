บทที่ 4
ผลการพัฒนาและทดสอบระบบ

บทนี้นำเสนอผลการพัฒนาระบบบริหารจัดการห้องปฏิบัติการคอมพิวเตอร์ อาคาร 75 ปี มหาวิทยาลัยราชภัฏวไลยอลงกรณ์ ในพระบรมราชูปถัมภ์ ผ่านระบบจองและยืม-คืนกุญแจออนไลน์ โดยครอบคลุมผลการพัฒนาหน้าจอหลักของระบบ ผลการทดสอบระบบ และผลการประเมินความพึงพอใจของผู้ใช้งาน

4.1 ผลการพัฒนาระบบ

การพัฒนาระบบบริหารจัดการห้องปฏิบัติการคอมพิวเตอร์ดำเนินการด้วย Next.js 16 (App Router) เป็น Framework หลัก, React 19 สำหรับส่วนติดต่อผู้ใช้, PostgreSQL เป็นฐานข้อมูล และ Prisma ORM สำหรับจัดการฐานข้อมูล ระบบรองรับผู้ใช้งาน 3 บทบาท ได้แก่ ผู้ดูแลระบบ อาจารย์ และนักศึกษา โดยมีหน้าจอหลักดังต่อไปนี้

4.1.1 หน้าจอเข้าสู่ระบบ (Login)

หน้าจอเข้าสู่ระบบรองรับผู้ใช้งานทั้ง 3 บทบาท โดยแยกประเภทการเข้าสู่ระบบผ่าน Tab สลับระหว่าง "นักศึกษา" (ใช้รหัสนักศึกษา 11 หลัก) และ "อาจารย์/เจ้าหน้าที่" (ใช้อีเมล) ระบบมีการป้องกัน Rate Limiting ผ่าน Upstash Redis โดยจำกัดการเข้าสู่ระบบไม่เกิน 10 ครั้งต่อนาทีต่อ IP เพื่อป้องกันการโจมตีแบบ Brute Force

[รูปที่ 4.1 — หน้าจอเข้าสู่ระบบ]

รูปที่ 4.1 หน้าจอเข้าสู่ระบบของระบบบริหารจัดการห้องปฏิบัติการ

4.1.2 หน้าจอ Dashboard

ระบบมี Dashboard แยกตามบทบาทของผู้ใช้งาน ดังนี้

  • Dashboard นักศึกษา แสดงสถิติการจองของตนเอง เมนูลัดสำหรับจองห้อง ดู QR Token และตรวจสอบตารางเรียน
  • Dashboard อาจารย์ แสดงคำขอจองที่รอการอนุมัติ สถิติการจอง และตารางสอนประจำสัปดาห์
  • Dashboard ผู้ดูแลระบบ แสดงภาพรวมระบบ ได้แก่ จำนวนห้อง สถานะกุญแจ จำนวนผู้ใช้งาน และสถิติการจองวันนี้
[รูปที่ 4.2 — หน้าจอ Dashboard แยกตามบทบาท]

รูปที่ 4.2 หน้าจอ Dashboard (ซ้าย: นักศึกษา, กลาง: อาจารย์, ขวา: แอดมิน)

4.1.3 หน้าจอจองห้องปฏิบัติการ

หน้าจอจองห้องปฏิบัติการให้ผู้ใช้เลือกห้อง วันที่ และช่วงเวลา (08:00–12:00 / 12:00–16:00 / 16:00–20:00) โดยระบบตรวจสอบ Conflict กับการจองอื่นแบบ Real-time ก่อนที่ผู้ใช้จะส่งคำขอ สำหรับนักศึกษาต้องระบุอาจารย์ผู้อนุมัติและสามารถเพิ่มผู้เข้าร่วมได้สูงสุด 4 คน

[รูปที่ 4.3 — หน้าจอจองห้องปฏิบัติการ]

รูปที่ 4.3 หน้าจอแบบฟอร์มจองห้องปฏิบัติการ

4.1.4 หน้าจออนุมัติคำขอจอง

อาจารย์สามารถตรวจสอบรายการคำขอจองที่รอการอนุมัติ โดยแสดงข้อมูลผู้จอง ห้อง วันที่ เวลา และจุดประสงค์ อาจารย์สามารถอนุมัติหรือปฏิเสธพร้อมระบุเหตุผลการปฏิเสธ ระบบจะแจ้งสถานะกลับไปยังนักศึกษาผู้จองทันที

[รูปที่ 4.4 — หน้าจออนุมัติคำขอจอง]

รูปที่ 4.4 หน้าจออนุมัติ/ปฏิเสธคำขอจองห้องปฏิบัติการ

4.1.5 หน้าจอยืม-คืนกุญแจ (Loan Desk)

เจ้าหน้าที่และอาจารย์ใช้หน้าจอนี้ในการดำเนินการยืมและคืนกุญแจ โดยสแกน QR Token จาก Smartphone ของผู้ใช้หรือกรอก Token โดยตรง ระบบตรวจสอบสิทธิ์การใช้งานโดยอ้างอิงจากรายการการจองที่ได้รับอนุมัติ และแสดงข้อมูลผู้จองก่อนยืนยัน หน้าจอยังแสดง Queue รายการที่รอ Check-in และกุญแจที่ถูกยืมอยู่

[รูปที่ 4.5 — หน้าจอยืม-คืนกุญแจ]

รูปที่ 4.5 หน้าจอยืม-คืนกุญแจ (Loan Desk)

4.1.6 หน้าจอ QR Token

ผู้ใช้งานสามารถแสดง QR Code ที่สร้างจาก JWT Token ซึ่งลงนามด้วย QR_TOKEN_SECRET เพื่อใช้ในการยืม-คืนกุญแจ Token มีอายุ 2 นาทีและรีเฟรชอัตโนมัติ พร้อมแสดง Countdown Timer เพื่อให้ผู้ใช้ทราบเวลาที่เหลือ

[รูปที่ 4.6 — หน้าจอ QR Token]

รูปที่ 4.6 หน้าจอ QR Token สำหรับยืม-คืนกุญแจ

4.1.7 หน้าจอสถานะห้องวันนี้ (Rooms Today)

หน้าจอสาธารณะแสดง Timeline การใช้งานห้องทุกห้องในรูปแบบตารางช่วงเวลา โดยใช้สีแยกแยะประเภทการใช้งาน ได้แก่ สีน้ำเงินสำหรับ IN_CLASS (ตาราง เรียน) สีเขียวสำหรับ AD_HOC (จองเฉพาะกิจ) และสีเทาสำหรับช่วงว่าง ผู้ใช้สามารถเลือกวันที่เพื่อดูสถานะล่วงหน้าได้

[รูปที่ 4.7 — หน้าจอสถานะห้องวันนี้]

รูปที่ 4.7 หน้าจอสถานะห้องวันนี้ (Rooms Today Timeline)

4.1.8 หน้าจอปฏิทินรายสัปดาห์

ปฏิทินรายสัปดาห์แสดงตารางเรียนและการจองในรูปแบบ Weekly Calendar แยกตามบทบาท โดยนักศึกษาจะเห็นวิชาที่ลงทะเบียนและการจอง AD_HOC ส่วนอาจารย์จะเห็นตารางสอนและการจองของตนเอง

[รูปที่ 4.8 — หน้าจอปฏิทินรายสัปดาห์]

รูปที่ 4.8 หน้าจอปฏิทินรายสัปดาห์ของนักศึกษา

4.1.9 หน้าจอ Kiosk Self-Check

หน้าจอ Kiosk ถูกออกแบบสำหรับอุปกรณ์ที่จอดรับ QR Token จากผู้ใช้โดยไม่ต้องล็อกอินเข้าระบบ โดยผู้ใช้เลือกห้อง เลือกโหมด (ยืม/คืน) และสแกน QR Code ผ่านกล้องของอุปกรณ์ Kiosk จะต้องผ่านกระบวนการ Pairing กับระบบก่อนผ่าน KioskToken

[รูปที่ 4.9 — หน้าจอ Kiosk Self-Check]

รูปที่ 4.9 หน้าจอ Kiosk Self-Check สำหรับยืม-คืนกุญแจด้วยตนเอง

4.1.10 หน้าจอรายงาน (Admin Reports)

ผู้ดูแลระบบสามารถกรองรายงานตามช่วงเวลา ประเภทการจอง สถานะ ห้อง และผู้จอง ระบบแสดง Summary Cards สรุปยอดรวมแต่ละสถานะ และตารางรายละเอียดพร้อม Pagination นอกจากนี้ยังรองรับการส่งออกเป็นไฟล์ PDF ผ่าน @react-pdf/renderer

[รูปที่ 4.10 — หน้าจอรายงาน]

รูปที่ 4.10 หน้าจอรายงานการจองห้องปฏิบัติการ (Admin Reports)

4.1.11 หน้าจอจัดการข้อมูลหลัก (Admin)

ผู้ดูแลระบบสามารถจัดการข้อมูลหลักของระบบผ่านหน้าจอจัดการ ได้แก่ จัดการผู้ใช้งาน จัดการห้องปฏิบัติการ จัดการกุญแจ จัดการรายวิชา กลุ่มเรียน และภาคการศึกษา ทุกหน้าจอรองรับการนำเข้าข้อมูลจำนวนมากผ่านไฟล์ CSV/XLSX พร้อม Dry-run Preview ก่อนนำเข้าจริง

[รูปที่ 4.11 — หน้าจอจัดการข้อมูลหลัก]

รูปที่ 4.11 หน้าจอจัดการข้อมูลผู้ใช้งานและข้อมูลห้องปฏิบัติการ

4.2 ผลการทดสอบระบบ

การทดสอบระบบดำเนินการโดยใช้วิธีการทดสอบแบบ Black-box Testing ซึ่งเป็นการทดสอบจากมุมมองของผู้ใช้งาน โดยไม่คำนึงถึงโครงสร้างภายใน โดยกำหนดกรณีทดสอบ (Test Case) ครอบคลุมฟังก์ชันการทำงานหลักทุกส่วน แล้วบันทึกผลการทดสอบเทียบกับผลที่คาดหวัง

4.2.1 กรณีทดสอบการเข้าสู่ระบบ

ตารางที่ 4.1 ผลการทดสอบการเข้าสู่ระบบ

ที่ กรณีทดสอบ ข้อมูลนำเข้า ผลที่คาดหวัง ผลการทดสอบ
1 เข้าสู่ระบบนักศึกษาสำเร็จ รหัสนักศึกษา 11 หลักที่ถูกต้อง + รหัสผ่านถูกต้อง เข้าสู่หน้า Dashboard นักศึกษา ผ่าน ✓
2 เข้าสู่ระบบอาจารย์สำเร็จ อีเมลที่ถูกต้อง + รหัสผ่านถูกต้อง เข้าสู่หน้า Dashboard อาจารย์ ผ่าน ✓
3 เข้าสู่ระบบแอดมินสำเร็จ อีเมลแอดมิน + รหัสผ่านถูกต้อง เข้าสู่หน้า Dashboard แอดมิน ผ่าน ✓
4 รหัสผ่านไม่ถูกต้อง รหัสนักศึกษาถูกต้อง + รหัสผ่านผิด แสดงข้อความ "รหัสผ่านไม่ถูกต้อง" ผ่าน ✓
5 รหัสนักศึกษาไม่ครบ 11 หลัก รหัสนักศึกษา 8 หลัก แสดงข้อความ Validation Error ผ่าน ✓
6 ล็อกอินเกิน Rate Limit (10 ครั้ง/นาที) กรอกข้อมูลผิดซ้ำ 11 ครั้ง ระบบบล็อก IP ชั่วคราว ผ่าน ✓
7 บัญชีถูกระงับ (isActive = false) รหัสนักศึกษา + รหัสผ่านถูกต้อง ปฏิเสธการเข้าสู่ระบบ ผ่าน ✓

4.2.2 กรณีทดสอบการจองห้องปฏิบัติการ

ตารางที่ 4.2 ผลการทดสอบการจองห้องปฏิบัติการ

ที่ กรณีทดสอบ ข้อมูลนำเข้า ผลที่คาดหวัง ผลการทดสอบ
1 นักศึกษาจอง AD_HOC สำเร็จ ห้อง LAB-A วันพรุ่งนี้ ช่วง 08:00–12:00 เลือกอาจารย์ผู้อนุมัติ สร้างการจองสถานะ PENDING ผ่าน ✓
2 อาจารย์จองสำเร็จ (อนุมัติอัตโนมัติ) ห้อง LAB-B วันนี้ ช่วง 12:00–16:00 สร้างการจองสถานะ APPROVED ทันที ผ่าน ✓
3 จองซ้ำช่วงเวลาที่มีการจองอยู่ ห้อง LAB-A วันที่มีการจองแล้ว ช่วงเวลาเดิม แสดงข้อความ "ห้องนี้ถูกจองแล้ว" ผ่าน ✓
4 จองวันที่เกิน 30 วัน เลือกวันที่เกิน 30 วันนับจากวันนี้ Date Picker ปิดวันดังกล่าว เลือกไม่ได้ ผ่าน ✓
5 เพิ่มผู้เข้าร่วมเกิน 4 คน เพิ่มผู้เข้าร่วมคนที่ 5 แสดงข้อความ "ผู้เข้าร่วมเต็มแล้ว" ผ่าน ✓
6 เลือก 2 ช่วงเวลาต่อเนื่อง เลือกช่วง 08:00–12:00 และ 12:00–16:00 สร้างการจองสถานะ PENDING ผ่าน ✓
7 เลือกช่วงเวลาไม่ต่อเนื่อง เลือกช่วง 08:00–12:00 และ 16:00–20:00 แสดงข้อความ "ต้องเลือกช่วงเวลาต่อเนื่อง" ผ่าน ✓
8 ยกเลิกการจองที่สถานะ PENDING กดยกเลิกการจองของตนเอง เปลี่ยนสถานะเป็น CANCELLED ผ่าน ✓

4.2.3 กรณีทดสอบการอนุมัติ/ปฏิเสธการจอง

ตารางที่ 4.3 ผลการทดสอบการอนุมัติ/ปฏิเสธการจอง

ที่ กรณีทดสอบ ข้อมูลนำเข้า ผลที่คาดหวัง ผลการทดสอบ
1 อาจารย์อนุมัติคำขอจอง กดปุ่มอนุมัติบนรายการที่สถานะ PENDING เปลี่ยนสถานะเป็น APPROVED ผ่าน ✓
2 อาจารย์ปฏิเสธพร้อมระบุเหตุผล กดปฏิเสธ ระบุเหตุผล กดยืนยัน เปลี่ยนสถานะเป็น REJECTED บันทึกเหตุผล ผ่าน ✓
3 ปฏิเสธโดยไม่ระบุเหตุผล กดยืนยันการปฏิเสธโดยไม่กรอกเหตุผล แสดงข้อผิดพลาด "กรุณาระบุเหตุผล" ผ่าน ✓
4 นักศึกษาไม่มาตามนัด (No-show) ไม่มี Check-in ภายใน 30 นาทีหลังเวลาเริ่ม ระบบ Cron เปลี่ยนสถานะเป็น NO_SHOW อัตโนมัติ ผ่าน ✓

4.2.4 กรณีทดสอบการยืม-คืนกุญแจ

ตารางที่ 4.4 ผลการทดสอบการยืม-คืนกุญแจ

ที่ กรณีทดสอบ ข้อมูลนำเข้า ผลที่คาดหวัง ผลการทดสอบ
1 ยืมกุญแจสำเร็จ สแกน QR Token ที่ถูกต้อง มีการจองที่อนุมัติแล้ว สร้าง Loan, กุญแจสถานะ BORROWED, การจองสถานะ CHECKED_IN ผ่าน ✓
2 QR Token หมดอายุ สแกน QR Token ที่หมดอายุเกิน 2 นาที แสดงข้อความ "Token หมดอายุ" ผ่าน ✓
3 ผู้ไม่มีสิทธิ์ยืมกุญแจ สแกน QR ของผู้ที่ไม่ใช่ผู้จองและไม่ใช่ผู้เข้าร่วม แสดงข้อความ "ไม่มีสิทธิ์ใช้ห้องนี้" ผ่าน ✓
4 คืนกุญแจสำเร็จ สแกน QR Token ของผู้ยืม อัปเดต Loan.checkedOutAt, กุญแจ AVAILABLE, การจอง COMPLETED ผ่าน ✓
5 อนุญาตยืมล่าช้า (Admin Override) สแกน QR หลังเวลาเริ่ม 30 นาที เปิด Override ยืมกุญแจได้และบันทึก Override Flag ผ่าน ✓
6 ทดสอบผ่าน Kiosk Self-Check เลือกห้อง, โหมดยืม, สแกน QR ผ่านกล้อง Kiosk ยืมกุญแจสำเร็จโดยไม่ต้องล็อกอิน ผ่าน ✓

4.2.5 กรณีทดสอบการจัดการข้อมูล (Admin)

ตารางที่ 4.5 ผลการทดสอบการจัดการข้อมูลโดยผู้ดูแลระบบ

ที่ กรณีทดสอบ ข้อมูลนำเข้า ผลที่คาดหวัง ผลการทดสอบ
1 เพิ่มผู้ใช้งานทีละคน กรอกข้อมูลครบถ้วน บทบาท STUDENT สร้าง User ใหม่ในระบบ ผ่าน ✓
2 นำเข้าผู้ใช้จาก CSV (Dry-run) ไฟล์ CSV 50 รายการ แสดงผล Preview รายการที่สำเร็จ/ผิดพลาด/ซ้ำ ผ่าน ✓
3 นำเข้าผู้ใช้จาก CSV (จริง) ยืนยันการนำเข้าหลัง Dry-run บันทึกเฉพาะรายการที่ผ่าน Validation ผ่าน ✓
4 เพิ่มห้องปฏิบัติการ กรอกรหัสห้อง ชื่อ ชั้น จำนวนคอมพิวเตอร์ สร้างห้องใหม่และแสดงในรายการ ผ่าน ✓
5 สร้างกลุ่มเรียนและ IN_CLASS Reservations เลือก Section และช่วงวันที่ ระบบสร้าง Reservation สำหรับทุกวันที่มีการเรียน ผ่าน ✓
6 Export รายงาน PDF กรองวันที่ พฤษภาคม 2568 กดส่งออก ดาวน์โหลดไฟล์ PDF ที่มีข้อมูลครบถ้วน ผ่าน ✓

4.3 ผลการประเมินประสิทธิภาพระบบโดยผู้เชี่ยวชาญ

ประเมินประสิทธิภาพของระบบโดยผู้เชี่ยวชาญด้านคอมพิวเตอร์จำนวน 3 ท่าน ประกอบด้วย ผู้เชี่ยวชาญด้านการพัฒนา Web Application ผู้เชี่ยวชาญด้านระบบสารสนเทศ และผู้เชี่ยวชาญด้านฐานข้อมูล โดยใช้แบบประเมินมาตราส่วน 5 ระดับ ตั้งแต่ 1 (น้อยที่สุด) ถึง 5 (มากที่สุด)

4.4 ผลการประเมินความพึงพอใจของผู้ใช้งาน

ทำการประเมินความพึงพอใจของผู้ใช้งานระบบ โดยใช้กลุ่มตัวอย่างแบบเจาะจง (Purposive Sampling) จากผู้ที่มีส่วนเกี่ยวข้องกับการใช้ห้องปฏิบัติการคอมพิวเตอร์ อาคาร 75 ปี มหาวิทยาลัยราชภัฏวไลยอลงกรณ์ ในพระบรมราชูปถัมภ์ จำนวน 30 คน ประกอบด้วยนักศึกษา 20 คน อาจารย์ 7 คน และเจ้าหน้าที่ 3 คน โดยใช้แบบสอบถามมาตราส่วน 5 ระดับ
